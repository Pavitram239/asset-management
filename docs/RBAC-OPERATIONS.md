# Deployment and operations

These are baseline operations and historical RBAC verification limits. Onboarding and location scopes are now locally implemented; later stock/custody/purchasing workflows remain planned in the [technical blueprint](TECHNICAL-BLUEPRINT.md). The [PRD](../PRD.md) governs target scope; apply additional rollout steps only with their implemented migrations and verified environment. No deployment is authorized by this guide alone.

## Company foundation: migrations 003 and 004

The [company-foundation report](COMPANY-FOUNDATION-VERIFICATION.md) records the current locally verified addition. Migration 003 adds protected owners, nullable currency/time-zone settings, company versions, an email-verification marker and command records. Migration 004 makes committed command identity/result pointers immutable while allowing response-cache removal. These were tested in isolated schemas only, not applied to the application database during development.

For a reviewed upgrade, back up first, stop incompatible instances, apply numbered migrations with the deployment identity and deploy matching API/frontend. Do not change existing migration checksums. Existing companies retain their old grants and show ownership awaiting review; role names never become protected ownership automatically. A trusted operator can explicitly map a chosen active member with `npm run ownership:review --workspace=server -- company-uuid registered-email`. The script verifies applied checksums, locks the chosen company, refuses an already-activated mapping and records an operator-review audit event. It adds ownership.manage and explicit delivered configuration/catalog/inventory/cost/file capabilities for that reviewed owner, and leaves email verification unchanged. Keep a separate active access administrator as well as an active owner.

The empty-installation bootstrap now records that explicit review for its chosen account. Later owner appointments require verified active colleagues; verification delivery/recovery remains B03 work. Never mark all legacy addresses verified to bypass that requirement. A removed owner's other grants remain, so review those separately when a person leaves. Ordinary membership and owner removals enforce last-owner continuity; direct operator actions still require deliberate review and restricted credentials.

Grant the runtime only required access to the new tables/functions and preserve restrictions on audit/history. Do not grant TRUNCATE on audit_events or api_commands. Keep committed command identities/result pointers when pruning response caches. No cache-pruning schedule/retention period is configured by this slice. Currency/time-zone edits require expectedVersion; no purchase-currency migration is implemented because procurement is still planned.

## Runtime and upgrade
Use Node 22.12+ and PostgreSQL 15+ (Compose uses 17). The server and frontend builder images now use Node 22. Firebase Admin 14 requires Node 22. Vite 8 and React Router 7 were upgraded for audited security fixes; do not use the previous lockfile. Run `npm ci` from the root. The server development command uses built-in `node --watch`; nodemon was removed.

This change has NOT been applied to the running application database. Verification used only the dedicated `asset_management_test` database and generated temporary schemas. Back up the application database and storage before deploying.

1. Review legacy administrator accounts (`SELECT id,email FROM users WHERE role='admin'`) and department/assignment consistency. The migration aborts atomically if legacy users exist without an administrator. Have an operator choose an existing account and provision a reviewed legacy administrator before retrying; do not make the first incoming signup an administrator. Never change migration 001.
2. Review mismatched old assignments with `SELECT p.id,p.department_code,u.department_code FROM products p JOIN users u ON u.id=p.assigned_to_id WHERE p.department_code IS DISTINCT FROM u.department_code`. Migration preserves these rows and captures their current assignment at migration time; it cannot reconstruct prior transfer history. Reconcile each mismatch deliberately. The new API requires active assignees in the asset department and blocks changing a member department until assigned assets are returned or transferred.
3. Stop old backend instances. Apply `npm run db:migrate` using the deployment database/schema owner. Migration 002 backfills a single legacy organization and configurable role/department records without deleting users or assets. The migration runner serializes and checksums migrations transactionally.
4. Deploy backend and frontend together. Old clients do not send required organization context. Users explicitly select an organization; no tenant is inferred from an asset ID. No code-based cross-organization bypass exists.
5. For an empty installation, register the intended owner, then run `npm run bootstrap:owner --workspace=server -- existing-owner-email "Organization name"`. This is operator-only and refuses an existing organizations table with records. Subsequent organizations require `organization.create` in the active organization. Provisioning creates an editable initial role; its name has no special meaning.
6. Verify access using two organizations and an account with no permissions before exposing the service.

Rollback requires a pre-deployment database backup and matching application version; there is no destructive automatic down migration. Stop writes before restore and account for writes since the backup. Deactivated organizations intentionally cannot be entered through normal tenant context; reactivation is an operator recovery action. Deleted assets are soft deleted; there is no purge or restore UI in this release.

## Production settings
- Set a random JWT_SECRET of at least 32 characters; startup rejects shorter production secrets. Keep JWT_EXPIRES_IN bounded according to your session policy. Cookie expiration follows the signed token expiration. HS256 is explicitly allowed; role claims in tokens are ignored.
- Set COOKIE_SECURE=true for HTTPS. Compose explicitly uses false for local HTTP and a sample development database password. Replace those values for hosted deployments. Do not expose the database or server directly on a public interface.
- Set TRUST_PROXY_HOPS=0 for direct access. Set 1 only if every connection passes through the trusted reverse proxy; Compose does so. Nginx replaces forwarded client IPs and preserves Host. Vite preserves Host too, allowing the same-origin mutation check to operate through its development proxy.
- Do not enable permissive CORS. Cookie-authenticated mutations reject mismatched Origin and cross-site Fetch Metadata. Requests without browser Origin are still subject to authentication, scope, and input validation.
- Use separate migration and runtime database identities. Runtime must be non-owner/non-superuser, with only needed SELECT/INSERT/UPDATE/DELETE privileges, sequence usage, and INSERT/SELECT on audit_events. Do not grant DELETE/UPDATE/TRUNCATE on audit_events, CREATE on the application schema, schema ownership, or BYPASSRLS. Audit triggers reject update/delete/truncate even for ordinary sessions. Owners/superusers can bypass database controls.
- Run migrations in the deployment step with its separate identity, then set RUN_MIGRATIONS=false for the runtime. Startup verifies all migration checksums using SELECT only. Local development defaults to RUN_MIGRATIONS=true for automatic migrations.
- API errors include a request ID and generic 500 response, with structured server failure logs that omit request bodies, cookies, and tokens. Authentication and authorization denials are appended to audit storage when available. Audit-storage failures emit a structured availability event. Forward logs to your deployment monitoring system.

## Private file storage: required before production

Onboarding update: migration 007 now enables verified self-service new-company ownership and employee invitations; [onboarding evidence](WORKSPACE-ONBOARDING-VERIFICATION.md) documents starter roles, delegation/revocation checks, API compatibility and local-only mail. Deploy only with matching API/worker/frontend revisions after normal environment review. Existing organizations are not silently assigned owners/roles or verified users.
Asset files now use Firebase Admin / Google Cloud Storage with opaque keys. Set FIREBASE_STORAGE_BUCKET to the bucket name and configure workload identity or GOOGLE_APPLICATION_CREDENTIALS pointing to a mounted, read-only service-account file. Never copy credentials into an image or commit them. Give the service account only the required bucket permissions. Docker does not automatically mount a credential file: add a deployment-specific read-only mount or workload identity.

Set Firebase client storage rules to deny unauthenticated direct reads/writes and remove public bucket/object IAM or ACL grants. The Admin SDK uses its server identity. Existing Firebase download URLs remain valid outside the application until their firebaseStorageDownloadTokens metadata is revoked; changing the application code or security rules alone does not revoke those bearer URLs. Inventory existing objects, back up metadata, remove legacy tokens with an authorized storage operator, and verify old URLs fail before declaring invoices private. This step was not executed here because no live storage credentials were used.

New file responses expose only authorized API URLs. The download context is an explicit header, or a query organizationId for browser images/links, and is validated against current membership. Downloads are bounded to 5 MB, no-store, type allowlisted, sandboxed, and audited. Files use random object names; extension, declared MIME and signature must match. Image pixel limits reduce decompression risk. Avatar maximum is 0.5 MB, other files 5 MB. PDF signatures are not a malware scan: deploy scanning/quarantine if your organization requires it.

Every upload gets a durable storage_cleanup intent before the external write. Asset/database/audit/history writes are transactional. A failed save leaves its intent for cleanup; successful live references are retained. Replacements queue old files, with a 24-hour grace period protecting in-flight requests. Cloudinary avatars follow the same intent pattern. Run `npm run storage:cleanup --workspace=server` periodically as one operator job, with the same private storage identities. Each run handles up to 100 entries; failures retain pending work for retry. It also prunes expired shared rate-limit entries. Monitor backlog age/count and job failures. Soft-deleted assets retain their files for a future documented retention/purge policy.

Live Firebase/Cloudinary success, provider timeouts and provider 5xx recovery were not exercised. Test these using a dedicated non-production bucket/account before rollout. Local tests prove authorization, invalid/oversized input rejection, and no asset insert when storage configuration fails; they do not establish live provider behavior.

## Permission and retention details
Permissions combine as a union of current active roles and direct grants in the selected active membership. A department-scoped role cannot grant organization management. Administrative permissions require organization scope; resource permissions support department and assigned-user scope. No implicit permission bundles, explicit deny, nested roles, or location restrictions are implemented. Locations are not modeled on current assets. Read permission is independent of write permission; a write-only response returns only the asset ID. Directory/statistics grants are separate from asset grants; asset editors who need assignment dropdowns also need directory.read.

The administrator guard protects at least one active user with organization-scoped access.manage. Access changes and asset writes serialize on the organization row and resolve grants again inside the transaction. Users cannot assign/revoke their own access, change their own membership, or change permissions/activation of a role assigned to themselves. Rename is permitted. Another authorized administrator must make those changes.

Warranty status is computed from the date in SQL using the UTC calendar, independent of the database session timezone. Existing expiration semantics are preserved: warrantyDate is the first expired day. Empty dates use the persisted fallback status, and clearing a date through the new API sets expired.

Legacy administrative membership assignment still uses a registered account; the new invitation flow also supports inviting an email before registration. Email verification/recovery/session revocation now have [local delivery operations](DELIVERY-OPERATIONS.md) and [verification evidence](IDENTITY-DELIVERY-VERIFICATION.md), using capture rather than a live provider. Apply migrations through 007 and configure the separate worker with its own encryption key before exercising those workflows. Capture is refused in production, so live account mail remains a deployment dependency. SSO/MFA are not introduced. Audit export/retention, location scopes and asset purge remain separate delivery work. Role/member collections have no pagination yet. Last-owner and last-administrator protections remain independent; review direct operator SQL and global account changes deliberately.

## Catalog/opening/private-file upgrade (010/011)

Review the explicit protected-owner capability mapping, then deploy only with authorization and matching migrations/frontend. Existing custom roles do not gain new resource/cost/file access automatically. Catalogue-linked individual writes through legacy PATCH/DELETE are gated; unlinked legacy cutover remains B08. Grant new-table access only to required runtime/operator identities and preserve immutable history/link/command restrictions.

The storage cleanup operator now verifies migration checksums before reading metadata. It protects linked private objects and unexpired 24-hour staging, and processes durable removal/orphan cleanup intents after its existing grace period. An upload response wait is capped at 20 seconds; unknown configured-provider outcomes and cleanup need the B23 provider/restore/runtime-role rehearsal. No successful provider upload/download/deletion or application-database migration was performed here; see [catalog evidence](CATALOG-INVENTORY-VERIFICATION.md).
